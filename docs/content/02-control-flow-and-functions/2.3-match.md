# 2.3 match

## Objectives

After this lesson the learner can:

- Choose between values with `match` on integers, strings and `bool`, with `_` for the rest. [L636]
- Use `match` as an expression whose arms have one type. [L636]
- Add guards (`_ if n < 0 =>`) and or-patterns (`1 | 2 =>`), and know a guarded arm doesn't count toward covering every case. [L636, L638, L642] (the outline's `n if n < 0 =>` is refused at the top level in m159; see Notes)
- Surprises: a `match` must cover every case, so integers and strings always need `_` (E0417); an unreachable arm is warning W0102. [L638, L640]

## Step 1: match expressions
Kind: read

Like an `if`, a `match` is an expression: it gives the value after `=>` in the first arm whose pattern matches.
Here `day` is `3`, so the arm on line 6 matches and `name` becomes `"Wednesday"`.
The `_` on line 7 matches anything, so it catches every number the other arms don't.
Press Run, then change `3` on line 2 to see the other arms.

Every arm must give the same type, so a number in place of `"Tuesday"` would be E0401.

```lugha
fun main() {
    let day = 3;
    let name = match day {
        1 => "Monday",
        2 => "Tuesday",
        3 => "Wednesday",
        _ => "another day",
    };
    println(name);
}
```

Output:

```text
Wednesday
```

## Step 2: Or-patterns
Kind: read

An arm can also take more than one value.
Line 4 has two patterns joined by `|`, and the arm matches when either does.
`day` is `6`, so it prints `weekend`.
Change `6` on line 2 to `7` and it still prints `weekend`, and any other number gives `weekday`.

```lugha
fun main() {
    let day = 6;
    let kind = match day {
        6 | 7 => "weekend",
        _ => "weekday",
    };
    println(kind);
}
```

Output:

```text
weekend
```

## Step 3: Exhaustiveness
Kind: fix (start gives E0417 "non-exhaustive match: other values of `string` are not covered", help "add `_ => …` as the last arm")

This `match` is on a string, with an arm for each of the three commands, and `command` is `"stop"`.
Will it compile without a `_`?

`lughac` refuses it with E0417, "non-exhaustive match: other values of `string` are not covered".
A `match` must cover every value `command` could hold, and `command` could be any string.
Integers are the same, so a `match` on a string or an integer always needs a `_`.
A `bool` doesn't need one, since `true` and `false` cover it.
Add the arm the help asks for, on line 7:

```lugha {7}
fun main() {
    let command = "stop";
    let speed = match command {
        "go" => 10,
        "slow" => 3,
        "stop" => 0,
        _ => 0,
    };
    println(speed);
}
```

Start:

```lugha

        "go" => 10,
        "slow" => 3,
        "stop" => 0,
    };

```

Solution:

```lugha

        "slow" => 3,
        "stop" => 0,
        _ => 0,

}
```

```text

```

## Step 4: Match guards
Kind: fix (start gives E0417 "non-exhaustive match: other values of `i64` are not covered")

An arm can have a condition, written after the pattern with `if`, as on lines 5 and 6.
The arm matches only when the pattern matches and the condition is true.
Between them, `0`, below zero and above zero cover every number, so does this `match` cover every case?

It gives E0417 again.
When `lughac` checks that every value is covered, it counts only the arms without a condition.
So the last case has to be an arm without one:

```lugha {6}
fun main() {
    let temperature = -4;
    let advice = match temperature {
        0 => "exactly zero",
        _ if temperature < 0 => "below zero",
        _ => "above zero",
    };
    println(advice);
}
```

Take `if temperature > 0` off line 6 and run again, or press Solve.

Start:

```lugha
fun main() {
    let temperature = -4;
    let advice = match temperature {
        0 => "exactly zero",
        _ if temperature < 0 => "below zero",
        _ if temperature > 0 => "above zero",
    };
    println(advice);
}
```

Solution:

```lugha
fun main() {
    let temperature = -4;
    let advice = match temperature {
        0 => "exactly zero",
        _ if temperature < 0 => "below zero",
        _ => "above zero",
    };
    println(advice);
}
```

Output (solution):

```text
below zero
```

## Step 5: Unreachable arms
Kind: fix (start runs, prints `another day`, with warning W0102 "unreachable match arm" on lines 5, 6 and 7)

The arms from step 1 are here, with `_` moved to the top, and `day` is still `3`.
It now prints `another day`, and `lughac` warns with W0102, "unreachable match arm", for lines 5, 6 and 7.
Arms are tried from the top, and `_` matches every number, so no value ever reaches the arms after it.
Move it back to the end:

```lugha {7}
fun main() {
```

## Notes

- Spec lines relied on: `match` is an expression, patterns are `_`, integer, `bool` or string literals or variants, guards, arms agree like `if`/`else` [L636]; exhaustiveness counts only arms without guards, `bool` covered by `true` and `false`, integers and strings need `_` [L638]; unreachable arms W0102 [L640]; or-patterns [L642]; arms are tried in order, from L636 ("if it is false, matching continues with the next arm") and W0102 [L640].
- Every program was run in the sandbox (pinned lughac m159) through the local API.
- Also checked: a number arm among strings is E0401 "integer literal where string expected", note "the first arm is string" (step 1's last sentence says "an error", not the code); `match raining { true => …, false => … }` with no `_` compiles.
- For `../lugha`, found while testing: a plain name as a top-level pattern, `t if t < 0 =>` or `n => "day {n}"` on an `i64`, gives E0403 "this pattern can't match a value of type `i64`" and E0301 "cannot find `t`". `mut t if t < 0 =>` works (the spec allows `mut x` at the top of an arm). The spec lists no plain top-level binding, so this may be by design, but the message reads as if `t` were taken for a variant, and the exhaustiveness line says integers need "a `_` or a binding". The outline's guard example used it, so the lesson uses `_ if temperature < 0` instead.
- Reader check (Python, JS/TS, Java/C readers), first draft: all seven answers right, with the `bool` and arm-type answers at 4 (stated, not run). All three stalled on step 4's "Change line 6's pattern to `_`" (it already was); two flagged "A string could be anything, and so could a number…" as the most machine-made line, one "not only the values this program happens to use". Open from readers, not taught here: naming the matched value inside a guard.
- Voice reviewer, first draft: step 4's instruction and "without a `_`"; "the one exception" was too broad (enums and `Option` too, L638); "a number" included `f64`; step 1 opened on a generic line; step 5's prediction was weak, now stated; "or press Solve" twice; step 3 moved after step 1 so the two coverage steps sit together. All taken.
