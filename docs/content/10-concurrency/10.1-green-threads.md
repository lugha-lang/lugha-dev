# 10.1 Green threads

## Objectives

After this lesson the learner can (one step each, titles from the outline):

1. **spawn**: a call in a new green thread; the spawner goes on. [L500, L588, L1184–1185]
2. **join**: `Task<T>`, `join` waits and gives a copy, again at once; spawning a closure. [L588–589, L878]
3. **No data races**: one OS thread, so a shared `Ref` needs no lock. [L1184]
4. **When main returns**: the program ends; running threads are dropped, their defers with them. [L12, L1188]

## Step 1: spawn
Kind: read

Until now each program has run one line of work, from the top of `main` down.
A green thread is another line of work in the same program, with its own stack of calls, and the program switches between them.
All of a program's green threads share its one OS thread and take turns on it.
`spawn` before a call starts the call in a new green thread, and `join` waits for one to finish.
Lines 11 and 12 spawn two, and `main` goes straight on to print "both started".
Press Run.

The two threads get their turns when `main` waits in `join` on line 14.
`task.yield_now()` on line 6, from `std.task`, hands over its turn, so their lines alternate.


```lugha
import std.task;

fun count(name: string, n: i64) {
    for i of range(1, n + 1) {
        println("{name} {i}");
        task.yield_now();
    }
}

fun main() {
    let a = spawn count("a", 3);
    let b = spawn count("b", 3);
    println("both started");
    a.join();
    b.join();
}
```

Output:

```text
both started
a 1
b 1
a 2
b 2
a 3
b 3
```

## Step 2: join
Kind: read

Each `spawn` gives back a handle to its thread.
`spawn square(3)` gives a `Task<i64>`, where `i64` is what the call returns; a call that returns nothing, like `count` in step 1, gives a plain `Task`.
`a.join()` waits for the thread to finish and gives a copy of its result, so line 6 adds 9 and 16 and prints 25.
Joining again, on line 7, gives another copy at once.
`spawn` also takes a closure followed by `()`, as on line 10, and it captures `k` by copy, as any closure does.
Press Run.

That copy is why `spawn xs.push(1)` is E0438: the new thread would push to its own copy of `xs`, and nobody would see it.


```lugha
fun square(n: i64): i64 = n * n;

fun main() {
    let a = spawn square(3);
    let b = spawn square(4);
    println(a.join() + b.join());
    println(a.join());

    let k = 2;
    let t = spawn fun(): string { "closure {k}" }();
    println(t.join());
}
```

Output:

```text
25
9
closure 2
```

## Step 3: No data races
Kind: read

This time both threads share one `Ref` box, and line 5 adds 1 to it 1000 times in each.
Press Run.

Only one green thread runs at any instant, so there are no data races: two threads never touch `total` at once.
A thread is switched out when it waits, and also after 4096 function calls and loop turns, so a long loop can't keep the others waiting.
That switch can fall between reading a value and writing it back.
Had line 5 read the total, yielded, then set it, both threads would often read the same value, and the program would print 1000.
Sharing one OS thread also means green threads never use two cores at once.


```lugha
import std.task;

fun add(total: Ref<i64>, n: i64) {
    for i of range(0, n) {
        total.update(fun(x: i64): i64 { x + 1 });
        task.yield_now();
    }
}

fun main() {
    let total = Ref.new(0);
    let a = spawn add(total, 1000);
    let b = spawn add(total, 1000);
    a.join();
    b.join();
    println(total.get());
}
```

Output:

```text
2000
```

## Step 4: When main returns
Kind: fix (start prints "work: started" and "main: done")

`work` sets a `defer` on line 4, prints, and sleeps for 100 milliseconds on line 6.
`task.yield_now()` on line 11 lets `work` start before `main` goes on.
Press Run.

"work: cleaned up" never prints.
When `main` returns, the program exits with `main`'s code, and green threads still running are dropped without running their defers.
So `main` has to `join` a thread it needs finished.
A panic in any green thread ends the program too, with exit code 101.
The fixed `main.la`:


```lugha {13}
import std.task;

fun work() {
    defer println("work: cleaned up");
    println("work: started");
    task.sleep(100);
}

fun main() {
    let t = spawn work();
    task.yield_now();
    println("main: done");
    t.join();
}
```

Add `t.join();` as line 13, or press Solve.

Start:

```lugha
import std.task;

fun work() {
    defer println("work: cleaned up");
    println("work: started");
    task.sleep(100);
}

fun main() {
    let t = spawn work();
    task.yield_now();
    println("main: done");
}
```

Output (start):

```text
work: started
main: done
```

Solution:

```lugha
import std.task;

fun work() {
    defer println("work: cleaned up");
    println("work: started");
    task.sleep(100);
}

fun main() {
    let t = spawn work();
    task.yield_now();
    println("main: done");
    t.join();
}
```

Output (solution):

```text
work: started
main: done
work: cleaned up
```

## Notes

- Spec lines relied on (m159): `spawn` syntax [L500]; `Task<T>`, `join` gives a copy, again at once [L588–589]; arguments evaluated at once, the rest captured by copy as by a closure [L878]; one OS thread, no data races, `Ref` needs no locks [L1184]; switching on waits, a new thread starts after the ready ones [L1185]; when `main` returns, running threads are dropped [L1188]; `std.task` has `sleep(ms)` and `yield_now()` [L12].
- Every program ran in the sandbox (pinned lughac m159) through the local API.
- Step 1's alternation comes from `yield_now`; without it, preemption every 4096 steps would let `a` print all three lines first [L1186].
- Step 2: `spawn xs.push(3)` gave E0438 in the sandbox ("`spawn` of a call that changes its receiver") [L604]. Step 3: the get, `yield_now`, set version of `add` printed 1000 in the sandbox; `update` itself is a call then a store [L1647], and a call can be preempted [L1186], so the step claims no more than this run. Step 4: a `panic` in a spawned thread exited 101 in the sandbox [L1188].
- Step 4: "without running their defers" is what the run shows (the deferred line never prints); the spec says the threads are dropped [L1188] and, in 6.4, that defers run when a function returns.
